Manual técnico del firmware Soundcraft Ui24R
Firmware 3.5.8328 • Análisis estático para desarrollar una aplicación de control • Edición 1 • 9 de septiembre de 2026
Este manual explica la arquitectura del paquete de actualización, la aplicación web recuperada, el protocolo de control y las reglas de interfaz que afectan a un cliente alternativo. Está dirigido al equipo que desarrolla la app de control de Gabriel Franco. Incluye fórmulas, estructuras de mensajes, parámetros, procedimientos y referencias que permiten volver al código de origen.
El paquete permite reconstruir una parte extensa del control remoto. También muestra que algunas operaciones visibles son secuencias de cambios ejecutadas por el navegador. Una app propia debe reproducir esas reglas cuando corresponda, además de enviar mensajes compatibles.
La consola del usuario declara 3.4.8318-ui24. El archivo analizado declara 3.5.8328. Este manual documenta la segunda versión; no certifica compatibilidad de cada función con la primera. El procesamiento DSP, las condiciones eléctricas y las respuestas de una consola real necesitan evidencia adicional a los archivos.

1 Alcance y lectura de la evidencia
Se verificó la integridad CRC de todos los miembros del ZIP, se calcularon huellas SHA256, se extrajeron las cuatro imágenes de disco y el ramdisk del kernel, y se recuperaron recursos comprimidos incrustados en el ejecutable del mezclador. Se analizaron sintácticamente los dos programas web principales sin iniciar los servicios de la consola ni ejecutar sus scripts de actualización.
Las referencias W1 y W2 indican el JavaScript original extraído de los recursos grandes. Sus números de línea corresponden al texto del primer script con contenido de cada HTML, conservando los saltos de línea originales. La referencia a una función permite localizarla incluso si se vuelve a formatear el archivo. Los offsets de recursos son bytes desde el inicio de umixsrv; las líneas JavaScript no son offsets binarios.

2 Identidad y estructura del paquete
El nombre recibido es uiupdate-k-3.5.8328-ui24v3.zip. El archivo target.id contiene soundcraft-ui24. Tanto etc/mixer.version como etc/system.version contienen 3.5.8328. El sufijo ui24v3 del ZIP no sustituye esos identificadores internos.
El ZIP contiene kernel.img, cuatro imágenes numeradas, preupdate.sh, update.sh, target.id y firmas .sig asociadas. Las imágenes 100-system.img y 200-mixer.img tienen estructuras ext reconocibles y se pudieron extraer con debugfs; las otras dos también fueron extraídas. kernel.img usa una cabecera Android boot image. Ese formato de empaquetado no significa que el equipo ejecute Android como sistema de usuario.
El inventario extraído contiene 918 archivos regulares: 168 en la imagen de mezclador, 195 en sistema, 11 en Xorg, 519 en Chrome y 25 en el ramdisk. No cuenta directorios ni enlaces simbólicos como archivos independientes. El ramdisk contiene 346 entradas al contar sus distintos tipos. El inventario de Chrome incluye bibliotecas, recursos, localizaciones y un perfil distribuido; no todo archivo corresponde a una función de mezcla.
Las firmas tienen 192 bytes cada una. Se constató su presencia; no se realizó una validación criptográfica con una clave pública de confianza. CRC y SHA256 permiten detectar cambios de contenido, pero no acreditan por sí solos el origen oficial.
Evidencia: ZIP y target.id; etc/mixer.version; etc/system.version; cabecera de kernel.img; inventarios de extracción.
3 Arranque y almacenamiento por capas
El script init del ramdisk monta devtmpfs, proc y sysfs. Define ROOT_DEVICE como /dev/mmcblk0p7 y USER_DEVICE como /dev/mmcblk0p1. Comprueba los sistemas de archivos con e2fsck y monta primero la base de sistema en solo lectura. Esas rutas pertenecen al esquema observado en el paquete; no deben reutilizarse como destinos de escritura desde la app de control.
Después monta la partición de usuario, recorre sus archivos /fs/*.img en orden de versión y monta cada imagen en solo lectura. Construye un sistema de archivos unionfs con la capa de usuario escribible por encima de las imágenes y de la base. Al final mueve los montajes de dispositivos y transfiere el arranque a systemd mediante switch_root.
Esto explica por qué una configuración que vemos dentro del firmware puede diferir de la consola instalada: la capa de usuario puede sustituir archivos de las imágenes. También explica por qué el paquete de actualización no equivale a una copia íntegra de la memoria interna. La base almacenada en p7, la configuración del usuario y sus shows no están incluidos íntegramente en este ZIP.
Si una imagen se monta correctamente, init elimina su copia .old. Si el montaje falla y existe una copia .old, elimina la imagen fallida y restaura el nombre anterior. El script no vuelve a montar explícitamente esa imagen restaurada dentro de la misma iteración. Por ello no debe describirse como una recuperación transaccional completa e inmediata.
El arranque limita scaling_max_freq a 1008000 y reconfigura un controlador USB para mantener un hub en modo high speed. Son ajustes de este script, no mediciones de temperatura, frecuencia efectiva o capacidad de alimentación USB. No hay base aquí para deducir que se pueda alimentar un ventilador determinado.
Evidencia: B1, init del ramdisk, variables ROOT_DEVICE, USER_DEVICE y DIRS; montaje unionfs y bloque de imágenes .old.
4 Actualización y recuperación
preupdate.sh crea /var/update, descomprime las imágenes y el kernel, comunica el progreso mediante /tmp/umixpipe0, verifica kernel.img con verifyfile y, si la verificación permite la operación, lo copia a /dev/mmcblk0p6. Después conserva las imágenes anteriores con extensión .old y mueve las nuevas a /fs. Finalmente solicita reiniciar. update.sh, en este paquete concreto, termina con exit 0 sin realizar otras tareas activas.
El script borra cachés de Chrome durante la actualización. No modifica la interfaz por un mecanismo separado: los recursos web principales están incrustados en el nuevo umixsrv que contiene 200-mixer.img.
Hay un detalle que merece revisión: la condición previa al flasheo compara las salidas completas de md5sum para un dispositivo y un archivo. Normalmente esas salidas contienen también nombres de ruta diferentes. La comparación podría resultar desigual aunque coincidan los hashes. Es una observación estática sobre la condición, no una prueba de actualización fallida ni de daño.
El script visible llama a verifyfile para el kernel, y el arranque verifica scripts de actualización antes de ejecutarlos. No se reconstruyó el flujo completo del verificador ni todas las verificaciones anteriores realizadas por umixsrv. No se debe concluir que las demás imágenes se aceptan sin verificación solo porque ese paso no aparezca en preupdate.sh.
El arranque distingue restauración de red, contraseña de configuración, bloqueo de la mezcla y restauración completa. Examina marcadores USB como netreset.txt, configpass.txt, masterpass.txt y fullreset.txt cuando se cumple la condición de recuperación. La restauración completa incluye formatear la partición de usuario y restaurar archivos de fábrica; no es un método de extracción. Las ramas destinadas a otros modelos no son instrucciones para la Ui24R.
Evidencia: U1 preupdate.sh; U2 update.sh; B1 init, bloques de verificación, reset y restauración de fábrica.
5 Servicios y componentes del sistema
umixsrv es un ejecutable ELF ARM de 32 bits, dinámicamente enlazado, de 19 559 892 bytes y sin símbolos de depuración. El servicio lo inicia en /mixer con el argumento -port=80. Tiene Restart=always, Nice=-10, prioridad de E/S best-effort 0 y afinidad CPU 0-3. El nombre del servicio es Ui Mixer Daemon.
Xorg y Chrome se ejecutan como servicios separados con prioridad de CPU y E/S inferior a la configurada para umixsrv. x.service usa Nice=17 y CPUAffinity=3. chrome.service usa Nice=17 y CPUAffinity=2,3. Son políticas solicitadas al planificador, no evidencia de que todos los núcleos estén ocupados o de que exista aislamiento de tiempo real garantizado.
startchrome.sh espera a que exista un servidor en 127.0.0.1:80 y abre http://127.0.0.1/mixer.html#local en modo kiosco. Configura DISPLAY=:0 y un perfil en /chrome/profile. La interfaz local usa por tanto el servidor HTTP del propio mezclador.
La imagen incluye Qt 5.3.2 Core, bibliotecas FFmpeg, mpv, glibc y módulos en lib/modules/3.4.111. Estos nombres ayudan a identificar dependencias, pero no demuestran las opciones de compilación ni el uso de cada biblioteca en todas las operaciones. La versión exacta de Chrome y el kernel en ejecución no se certificaron mediante una sesión en el equipo.
fw.jam, fw_scu.jam y ui24_Gowin.bin son artefactos binarios adicionales de hardware. Sus nombres y las cadenas SPI/UART del ejecutable justifican investigarlos por separado; no revelan por sí solos el diseño lógico de la placa ni los algoritmos DSP.
Evidencia: S1 umixsrv.service; S2 x.service; S3 chrome.service y startchrome.sh; ELF de umixsrv; inventario de bibliotecas.
6 Recursos web recuperados
Se identificaron 22 bloques comprimidos zlib con longitud descomprimida coherente, compatibles con recursos Qt. Entre ellos hay HTML, JavaScript, CSS, fuentes, SVG, un mapa de imágenes y un PNG. Este número describe los bloques recuperados por ese método; existen además recursos sin comprimir y contenido generado dinámicamente.
W1 procede del bloque en el offset 18429544 de umixsrv y contiene 1 292 140 bytes descomprimidos. W2 procede del offset 18752107 y contiene 862 652 bytes. W1 se identifica como aplicación tablet en sus constantes; W2 corresponde a la variante phone. W1 contiene 593 declaraciones de función y 2039 llamadas relevantes de acceso a estado, enlaces de controles o envío. W2 contiene 452 y 1446 respectivamente. Esas cifras incluyen funciones de bibliotecas; no equivalen a cantidades de funcionalidades.
La aplicación combina un modelo de estado JavaScript con widgets y dibujo Canvas. Incluye bibliotecas como Socket.IO 0.9.17; otros recursos identifican jQuery 1.10.2, Bootstrap 3.3.7, Bootstrap-select 1.12.1, teclado virtual, FastClick y WebGL-2D. Identificar componentes no equivale a realizar una auditoría de vulnerabilidades.
curSetup, netConfig y staticInitDataArray pueden proceder de contenido generado por el servidor. Los bloques standalone y emulación contienen configuraciones de ejemplo para otros modelos. No se deben usar sus cantidades de canales, claves ni direcciones como estado real de una Ui24R. configFunctions activa capacidades Ui24R cuando curSetup.input es al menos 20: ruteo, latencia, gate, matrices, cues, aislamiento y multipista.
Evidencia: W1 isStandalone, createData, configFunctions; W1 y W2 scripts principales; recursos W3 y W4 de configuración.
7 Transporte de control
La aplicación incorpora Socket.IO 0.9.17 con número de protocolo 1. netStart llama a io.connect y recibe eventos message. No es suficiente conectar una versión moderna de Socket.IO suponiendo compatibilidad de formato. Tampoco basta con enviar directamente SETD a un WebSocket sin reconstruir el encuadre y el establecimiento de sesión adecuados.
La biblioteca forma URLs con recurso socket.io, número de protocolo, transporte y sesión. El servidor contiene la ruta /socket.io/. El endpoint concreto y la respuesta de handshake de una unidad instalada deben registrarse durante la validación dinámica. No se ha demostrado que todos los transportes alternativos incluidos en la biblioteca cliente estén implementados por el servidor.

8 Estado inicial y actualizaciones
dataValue es un diccionario de claves a valores. getValue devuelve null si no encuentra una clave. setValueX escribe primero en ese diccionario y después intenta enviar el cambio. Esta actualización es optimista: el envío puede fallar por desconexión y el valor local ya haber cambiado. Una app propia debería separar valor confirmado, edición pendiente y estado de conexión.

receiveMessage separa primero por saltos de línea. receiveMessage2 utiliza split con límite 3 para SETD y SETS. No puede suponerse que el resto de una cadena con caracteres ^ se conserve. En nombres de escenas, la propia interfaz sustituye ^ por _. INIT mezcla propiedades en el diccionario existente; esa función no limpia primero las claves anteriores. Al reconectar o cambiar de unidad, la app propia debe establecer cómo invalida el estado viejo y cuándo considera completo el nuevo. No se ha identificado un número de revisión transaccional universal para las escrituras.
Una respuesta SETD observada confirma que el cliente recibió ese valor en el protocolo; no mide su efecto acústico. Una ventana de guardado puede mostrarse inmediatamente después de enviar un comando y pedir una lista nueva. No debe interpretarse automáticamente como confirmación durable del almacenamiento.
Evidencia: W1 getValue, setValueX, putValue, receiveMessage, receiveMessage2, parseCommand y controles de guardado de snapshots.

10 Reglas de escritura y estéreo
setValue aplica bloqueos, envía el cambio y, para ciertas familias y propiedades, genera escrituras adicionales para el canal enlazado o el envío estéreo. Por tanto, la sincronización visible de dos canales puede depender parcialmente del código del navegador. Un cliente alternativo necesita probar qué hace el servidor por sí mismo y qué debe reproducir.
stereoIndex usa 0 para una mitad y 1 para su pareja: el código busca el índice siguiente o anterior, respectivamente. No se debe confundir con un booleano de activación. El valor que representa ausencia de enlace debe leerse del estado y de las reglas de la tira; no se certifica aquí una enumeración universal por simple analogía.
La propagación genérica excluye gain, phantom, stereo, invert, delay, src, scsrc, r, color, name, stereoIndex y mtkrec. Pan también tiene tratamiento específico. Los envíos aux y mtx examinan el stereoIndex del bus destino y pueden construir otra clave. Copiar una propiedad sin sus excepciones produce comportamientos diferentes de la web oficial.
settings.block.pass y los ajustes settings.block.* participan en la validación de interfaz; settings.master_pass es una preferencia del cliente. isBlocked y setValue no usan una lógica trivial de verdadero igual a bloqueado en todos los casos. Se debe conservar la semántica de cada categoría y no deducirla solo del nombre.
La app propia debería centralizar estas reglas en una capa de comandos, con acciones explícitas como cambiarNivelDeParEstéreo. El componente visual no debería decidir por su cuenta qué claves adicionales escribir. Los cambios recibidos de la consola deben actualizar la vista sin iniciar otro ciclo de escrituras.
Evidencia: W1 setValue, setValueX, isBlocked; controles stereoIndex y enlaces aux y mtx.
11 Nivel ganancia phantom y retardo
mix y los valores de envío usan una posición normalizada cuya relación con amplitud y dB no es lineal. VtoLIN contiene una aproximación exponencial polinómica con corrección cerca de cero. VtoDBf calcula dB desde esa amplitud; DBtoVf resuelve la inversa por búsqueda binaria, con límites explícitos para -200 y +10 dB. El valor zeroDbPos es 0.7647058823529421.
Las versiones VtoDB y VtoDB2 formatean texto y usan reglas de redondeo y representación de silencio. No deben usarse como funciones numéricas de una automatización. El anexo conserva la fórmula de VtoLIN y ejemplos calculados a partir de la función numérica.
VtoGAIN24 cuantiza la posición en 64 índices, consulta ui24pgains y resta 1. La tabla tiene pasos repetidos en su parte baja y pasos distintos en la alta. Su salida va de -6 a 57 según esa tabla. GAIN24toV calcula otra normalización lineal; no es una inversa exacta para todos los escalones. Esto merece un test explícito de ida y vuelta antes de implementar escritura por dB.
La interfaz define PHANTOM_ON_DELAY=4000 y PHANTOM_OFF_DELAY=17000 como temporizaciones de control visual. No prueban el tiempo eléctrico de carga o descarga. También distingue phantom, hiz e invert, y bloquea controles de ganancia según la fuente elegida. Escribir phantom requiere resolver el previo físico afectado y respetar el flujo de confirmación del producto.
Los retardos se manejan en segundos. askForDelay convierte milisegundos, muestras, metros, pies y expresiones de tiempo antes de validar el máximo pasado por cada control. W1 define SAMPLE_RATE=44100 para esas conversiones y no se encontró otra asignación en ese script. Esto documenta la conversión de la interfaz, no certifica por sí solo la frecuencia efectiva del motor de audio.
Evidencia: W1 VtoLIN, VtoDBf, DBtoVf, ui24pgains, VtoGAIN24, GAIN24toV, askForDelay, VtoLATENCY y blockGainBySrc.
12 Ecualización y supresión de realimentación
La EQ paramétrica de canal usa ramas eq.b1 a eq.b4 con freq, q y gain, además de HPF, LPF y sus pendientes. La interfaz también contiene referencias a b5 en contextos concretos; su presencia no convierte todas las EQ de canal en cinco bandas. Debe respetarse el widget y el tipo de tira que origina cada referencia.
FREQtoV y VtoFREQ relacionan la posición con una escala logarítmica de 20 a 22050 Hz. VtoQ transforma a Q entre 0.05 y 15. VtoEQGAIN20 y VtoEQGAIN15 representan escalas distintas de ganancia. Hay que asociar cada una a su control, no elegir una escala global para cualquier EQ.
HPF interpreta exactamente cero como apagado; LPF interpreta exactamente uno como apagado. Estos valores son estados especiales, además de extremos numéricos. Un serializador que sustituya 0 por un pequeño epsilon puede encender un filtro que debía quedar desactivado.
resetGraphEQ recorre 31 bandas de EQ gráfica. En auxiliares utiliza eq.peak.n; en master utiliza eq.peak.l.n y eq.peak.r.n y el enlace eq.linked. Las ganancias neutras se restablecen a 0.5. Los HPF y LPF del master también tienen ramas izquierda y derecha.
AFS expone claves como afs.enabled, afs.fmode, afs.logic y afs.sensitivity. La interfaz solicita AFSUPDATEVAR, recibe información en var.afsdata y usa AFSLOADCHAN en su diálogo. Estos puntos permiten controlar y representar la función, pero no reconstruyen la detección de realimentación ni el diseño exacto de sus filtros automáticos.
Evidencia: W1 EQChannel, resetParEQ, resetGraphEQ, FREQtoV, VtoFREQ, VtoQ y controles AFS.
12 1 Deesser
El deesser utiliza deesser.enabled, deesser.freq, deesser.threshold y deesser.ratio. Su frecuencia visible se calcula con 2000*Math.pow(7.5,v), de 2000 a 15000 Hz. El umbral usa VtoTHRESH, de -90 a +6 dB; el ratio usa VtoDS_RATIO. Los extremos y el dibujo son parte del control recuperado y no revelan la selectividad espectral del DSP. resetParEQ incluye el restablecimiento de estas propiedades, por lo que la operación puede afectar más que las bandas de EQ.
Evidencia: W1 EQChannel, DeesserVtoFREQ, VtoDS_RATIO y resetParEQ.
13 Compresor gate y ducker
La dinámica usa claves dyn.threshold, dyn.ratio, dyn.attack, dyn.release, dyn.outgain, dyn.softknee, dyn.bypass y metadatos de preset. Master puede tener ramas dyn.l y dyn.r con dyn.linked. Existen propiedades históricas como dyn.gain o dyn.gate en presets; su presencia no implica que la web Ui24R moderna las utilice igual que otros modelos.
El ratio se representa mediante una función recíproca. En el extremo cero se obtiene infinito matemático, que algunos controles presentan como infinito. Ataque y release usan curvas basadas en desqr(v)=1-(1-v)*(1-v). El anexo muestra funciones y dominios numéricos separados del texto que presenta la interfaz.
Gate tiene su propio bloque gate.enabled, gate.bypass, gate.thresh, gate.attack, gate.release, gate.hold y gate.depth. resetGate lo habilita, desactiva bypass y asigna valores particulares; esa acción restablece el control, pero no demuestra que la puerta atenúe cualquier señal en ese estado. Profundidad y umbral deben analizarse junto con la señal entrante.
El selector ducker aparece en la interfaz de dinámica de subgrupos cuando el subgrupo tiene índice mayor que cero. Ofrece NONE y los subgrupos anteriores. Se enlaza con s.n.ducker. Esto confirma una restricción del selector y la existencia del parámetro; no confirma todos los detalles del detector ni del audio de control. Debe probarse con dos subgrupos y señal conocida.
scsrc significa fuente de soundcheck en la pantalla de ruteo. No debe documentarse como entrada sidechain del compresor por semejanza de abreviatura. La evidencia que lo relaciona con soundcheck es directa: el control SOUNDCHECK construye esas claves.
Evidencia: W1 DYNSubPage, controles de ducker, resetDyn, resetGate, VtoRATIO, VtoTHRESH y ruteo chansc.

15 Envíos auxiliares matrices y grupos
Los envíos utilizan rutas como i.n.aux.k.value, .pan, .mute, .post y .postproc. value no está expresado directamente en dB. post y postproc son selectores distintos: el punto respecto al fader y el punto respecto al procesamiento no deben fusionarse en un solo booleano sin revisar el control correspondiente.
Los envíos FX usan fx.k.value y fx.k.mute dentro del prefijo de la tira de origen. Las matrices usan mtx.k.value, .pan y .mute. Algunas familias y destinos tienen restricciones de visibilidad y enlace; la matriz no equivale a un auxiliar adicional independiente en todas las situaciones.
subgroup y vca aparecen como asignaciones de canal; resetChannel los restablece a -1 en las familias pertinentes. Un VCA es un control de grupo y tiene su propio mix y mute. La aplicación contempla propagación de estados y presentación de miembros; no basta con sumar sus valores como si fuera otra etapa de audio idéntica a un subgrupo.
mgmask existe como estado global y como pertenencia por tira. Los bits 0 a 5 corresponden a seis grupos de mute en el código. MUTEFX_BIT_IDX es 22 y MUTEALL_BIT_IDX es 23. La interfaz conserva bits al activar o desactivar uno; escribir la máscara completa a partir de un estado viejo puede anular cambios de otro cliente.
forceunmute interviene en excepciones de mute. muteGroupON reúne miembros, incluye ciertas relaciones VCA y limpia forceunmute antes de activar el grupo. Por eso no debe mostrarse mute efectivo usando únicamente la propiedad mute de la tira. Solo, máscara de grupos, VCA y excepciones deben modelarse por separado.
Los controles de escucha incluyen settings.soloMode, settings.solotype, settings.multiplesolo, settings.solovol, settings.hpvol.0, settings.hpvol.1 y settings.hpswap. Su alcance físico debe verificarse con la configuración de salidas.

17 Automix
La aplicación distingue grupos A y B. automix.a.on y automix.b.on activan sus controles; i.n.amixgroup asigna un canal. La interfaz usa -1 para no asignado, 0 para A y 1 para B. Al asignar un canal restablece amix a 0.5 y evita que permanezca en ambos grupos a la vez.
El selector impide agregar más de ocho canales a cada grupo. Esto confirma una restricción de la interfaz examinada; no demuestra por sí solo qué haría el servidor ante una escritura externa que exceda ese límite. La app propia debe respetarla en su comportamiento normal.
automix.time se convierte mediante VtoVMIX_TIME a 0.02 + 3.98*Math.pow(v,3.0517) segundos, con presentación en ms de aproximadamente 20 a 4000. amix usa VtoVMIX_WEIGHT, -12 + 24*v, para presentar un peso de -12 a +12. Esos pesos son controles del mezclador automático y no sustituyen directamente el fader de mezcla.
VUA transporta mediciones asociadas al Automix. El cliente decodifica Base64, toma una cantidad del byte 0 y los datos de canal desde el byte 4. Para los canales presentes en la lista de la ventana muestra 1-deconvertVU(byte). No se ha reconstruido el algoritmo DSP que produce esos valores.
Automix y ducker se documentan como funciones distintas. La presencia de Automix no demuestra que la consola haga una mezcla musical completa, ajuste EQ automáticamente o calcule ganancias óptimas para un show.
Evidencia: W1 controles AUTOMIX, parseVUAdata, VtoVMIX_TIME, VtoVMIX_WEIGHT y updateByKey.

21 Cascada reloj y sincronización de clientes
La aplicación utiliza el prefijo @ para dirigirse a la unidad secundaria cuando SLAVE_MODE está activo. sendMessage puede añadirlo automáticamente, salvo que reciba una indicación para omitir esa transformación. receiveMessage2 filtra mensajes de la otra unidad y trata de forma especial determinados mensajes BMSG.
switchUnit cambia SLAVE_MODE, solicita INIT y establece temporizadores de refresco y bloqueo temporal. isCascade consulta var.cascade.connected y otros estados de interfaz. Un único diccionario sin identidad de unidad puede mezclar datos si se cambia de consola antes de terminar de aplicar el nuevo estado.
Las claves settings.cascade.enabled, master, remote, mgsync, snapsync, vcasync y ch24solo controlan aspectos que la interfaz expone por separado. settings.clock tiene opciones de reloj interno o cascada en un selector condicionado por SHOW_WIP. Su presencia en el código no garantiza que esté visible normalmente. La sincronización de transporte de audio, la negociación entre unidades y la estabilidad del reloj no se reconstruyeron desde el código de pantalla.
BMSG^SYNC^id^selección sincroniza la selección de canal entre clientes que comparten sync_id y tienen habilitada la opción. BMSG^SYNC_VG hace algo equivalente con grupos de vista. Son mensajes de coordinación de interfaz, no mecanismos de sincronización de muestras de audio ni transacciones de configuración.
La app propia debe mantener identificadores separados para consola física, sesión de transporte, unidad de cascada y perfil local de usuario. Esto también facilita impedir que una automatización destinada al escenario principal se aplique por error a la secundaria.
Evidencia: W1 sendMessage, receiveMessage2, switchUnit, isCascade, parseBMessage y controles CASCADE.
22 Footswitch acciones externas y UDP
var.fswgpio y var.rswgpio se enlazan a indicadores de estado del footswitch y del pulsador de reset. Su presencia permite representar cambios recibidos por el protocolo; no garantiza una frecuencia de muestreo adecuada para cualquier uso musical. Se deben medir flancos, repetición y latencia antes de usar el footswitch como disparador crítico.
settings.footswitchfunc y settings.fsmgidx configuran acciones de pedal y selección de grupo. El selector asigna 0 a Mute FX, 1 a Mute All, 2 a Play, 3 a Record, 4 a Tap Tempo, 5 a MTK Play, 6 a MTK Record y 7 a Mute Group. Las acciones de teclas F1/F2 pertenecen además al cliente y pasan por doFfunc. Una configuración local de tecla no debe confundirse con una función física persistente del pedal.
La interfaz contiene un emisor UDP con forma UDP^host:puerto^contenido. Utiliza settings.udpcoms para almacenar configuraciones y settings.udpmsg para una respuesta o mensaje mostrado. Que exista este emisor no implica que todos los comandos del mezclador se acepten directamente en un puerto UDP público, ni que la Ui24R implemente una API OSC nativa.
IOSYS^ envía un contenido construido por controles externos y existen iosyscmd e iosysname en algunas tiras. HIQNET_DISCOVER también aparece en el catálogo. La gramática completa de los contenidos y los sistemas externos compatibles no se verificó; deben documentarse como integración a investigar, no como comandos arbitrarios de shell.
La app puede construir automatizaciones propias encima de funciones confirmadas: cargar una escena, escribir BPM, cambiar un envío o activar un grupo. Conviene que cada automatización declare destinos, precondiciones, estado esperado y cómo cancelar cambios pendientes al perder la conexión.
Evidencia: W1 getUdpReply, getUdpParam, setUdpSlot, iosys, doFfunc y controles de GPIO y footswitch.
23 Red y administración HTTP
La configuración distribuida define eth0 con 10.10.2.1/24 y wlan0 con 10.10.1.1/24. wlan0 habilita servidor DHCP con PoolOffset=10, PoolSize=100 y DNS 10.10.1.1. El archivo wlan1.network usa Name=wlan1.disabled y DHCP=ipv4. Estos son valores de la imagen, sujetos a sustitución por la capa de usuario.
dnsd.conf contiene una respuesta comodín a 10.10.1.1. Los servicios hostapd, wpasupplicant y dnsd corresponden al hotspot, cliente WiFi y resolución de nombres. No debe asumirse a partir de estas plantillas que ambas interfaces estén actualmente encendidas, que haya Internet o que Ethernet esté ofreciendo DHCP a un ordenador.
La página de administración contiene formularios POST a /config.html con application/x-www-form-urlencoded. W4 refresca datos desde js/netconfig.js. El HTML incluye sustituciones del servidor como <?netConfig?>. Guardar esa plantilla en un navegador sin el servidor no reproduce su funcionamiento completo.
La configuración diferencia ap_*, wlan_* y eth_*, e incluye datos configurados y obtenidos por DHCP. Hay campos de estado como enabled, up, ifid y mac. El frontend no sustituye las comprobaciones del servidor; setNetValue solo modifica el objeto local netConfig y redibuja, sin demostrar por sí mismo una escritura persistente.
El ejecutable contiene una respuesta HTTP 401 con autenticación Basic para configuración. La imagen incluye también un archivo telnetd.service. No se verificó su habilitación en la consola del usuario ni se intentó usarlo. No se incluyen credenciales ni hashes de cuentas porque no son necesarios para implementar el control normal.
Evidencia: N1 archivos systemd/network; N2 servicios de red y dnsd.conf; W3 HTML de configuración; W4 JavaScript de configuración; cadenas HTTP de M1.
24 Persistencia local y variantes de interfaz
settingsStorage y localStorage guardan preferencias del cliente: idioma, vista, opciones de dibujo, sincronización, permisos locales y opciones de tempo. dataValue contiene el estado que intercambia la aplicación con el mezclador. Aunque ambos usen nombres parecidos, no son el mismo almacén.
La interfaz tablet incluye procedimientos de cascada, grupos de vista, UDP y Automix que no aparecen bajo los mismos nombres en el script phone. La ausencia de una función con el mismo nombre no demuestra ausencia absoluta de la capacidad en la variante móvil; puede tener otro diseño o una implementación diferente.
initLocal detecta 127.0.0.1 o el fragmento #local. Se modifica el comportamiento visual y se utiliza el navegador en modo kiosco. El código también contiene rutas de demostración y emulación, importación y exportación JSON en el cliente y recursos multilenguaje. No deben confundirse con APIs del servidor.
Las tasas fps=60 y fps=30 para interfaz local son objetivos de dibujo observados, no tasas de telemetría de la consola ni de muestreo de audio. Deshabilitar VU en pantalla puede evitar trabajo de dibujo sin demostrar que el servidor deje de producir los mensajes.
Para Angular conviene mantener la recepción y el estado fuera del ciclo de renderizado de cada widget, agrupar actualizaciones de medidores y publicar cambios de parámetros por clave. Es una recomendación de arquitectura derivada del tráfico y del modelo, no una dependencia del firmware respecto a Angular.
Evidencia: W1 settingsStorage, initLocal, updater y preferencias de dibujo; comparación sintáctica W1 y W2; S3 startchrome.sh.

26 Arquitectura de implementación propuesta
Se recomienda separar transporte Socket.IO antiguo, codec de mensajes de aplicación, almacén de estado por unidad, diccionario de parámetros, operaciones compuestas y presentación. Los medidores tienen un flujo de alta frecuencia distinto de los comandos de usuario. La documentación del firmware no exige usar su biblioteca obsoleta directamente en el frontend; un adaptador compatible puede contener esa dependencia.

El análisis no reconstruye el código fuente C++ de umixsrv, la implementación completa de DSP, los programas lógicos de los archivos de hardware, el protocolo interno entre chips ni el esquema electrónico. El offset de la última columna es un índice de caracteres del texto JavaScript procesado, no una dirección de memoria ni un offset de byte dentro de umixsrv. Para recursos binarios se utilizan los offsets del anexo A.
Anexo I Reproducción del análisis
La extracción se realiza sobre copias locales y no necesita modificar la consola. El siguiente procedimiento requiere un entorno Linux con Python y debugfs. No ejecuta preupdate.sh, update.sh, init ni umixsrv.
python -m zipfile -e uiupdate-k-3.5.8328-ui24v3.zip firmware
mkdir -p mixer-extracted system-extracted xorg-extracted chrome-extracted
debugfs -R 'rdump / mixer-extracted' firmware/200-mixer.img
debugfs -R 'rdump / system-extracted' firmware/100-system.img
debugfs -R 'rdump / xorg-extracted' firmware/300-xorg.img
debugfs -R 'rdump / chrome-extracted' firmware/400-chrome.img
El lector de imágenes usado en el análisis no requiere montar las imágenes ni iniciar sus ejecutables. Se registra la versión de las herramientas y se conservan los hashes antes de generar representaciones reindentadas del código.
Extracción de los dos recursos principales
from pathlib import Path
import zlib
binary = Path("mixer-extracted/mixer/umixsrv").read_bytes()
for offset in (18429544, 18752107):
expected = int.from_bytes(binary[offset-4:offset], "big")
decoder = zlib.decompressobj()
payload = decoder.decompress(binary[offset:], expected + 1)
if not decoder.eof or len(payload) != expected:
raise ValueError("Recurso o versión incorrectos")
Path(f"resource-{offset}.html").write_bytes(payload)
Estos offsets son específicos del SHA256 documentado. No se aplican sin comprobarlos a una nueva versión. Para descubrir otros bloques se examinaron candidatos zlib precedidos por una longitud big-endian y se comprobó fin de flujo y tamaño. El script principal es el primer elemento script con contenido de cada HTML; el script externo vacío no cuenta.
Extracción del ramdisk
La cabecera Android informa kernel_size=9956176, ramdisk_size=2714272 y page_size=2048. El kernel empieza después de la página de cabecera. El ramdisk empieza en page_size + ceil(kernel_size/page_size)*page_size, que en este archivo da 9959424. Su carga gzip se descomprime a un archivo CPIO newc de 5607936 bytes. El inventario conserva modo, tamaño y destino de enlaces; para leer scripts basta extraer archivos regulares y evitar rutas que salgan del directorio elegido.
Cómo extender este manual
Para otra versión, repetir inventario y hashes, extraer recursos, comparar AST y claves, y conservar los cambios de fórmulas y emisores. Completar después con capturas de la unidad física. Una coincidencia de nombres entre versiones no prueba igualdad de semántica. Las fichas deben indicar la versión confirmada y la evidencia de cada excepción.
